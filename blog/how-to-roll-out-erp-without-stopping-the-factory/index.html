How to Roll Out a New ERP Without Stopping the Factory

A factory cannot close for a week to change software. Here is how to move to a new ERP one department at a time, with the old system still running beside it.

Most owners worry about the price of an ERP. Fewer worry about the day it goes live, and that day is where many projects fail. The software can be good and the launch can still go badly.

A factory cannot stop for a week to change its system. Orders keep coming, machines keep running and trucks keep leaving. So the new system has to come in while the work goes on.

This is the way I do it. It is the same way the ERP I built for a textile mill went into daily use across seven departments.

Why "everything on Monday" fails

The risky plan is the big switch: on Friday everyone uses the old system, on Monday everyone uses the new one.

It fails for simple reasons:

  • every department has questions on the same morning
  • one small mistake in one screen blocks the departments after it
  • nobody knows yet which numbers to trust
  • when people are under pressure, they go back to paper

After one bad week, staff decide the new system "does not work". That opinion is very hard to change later.

1. Start with one department

Pick one department and make it work fully before you touch the next one. A good first department has three things:

  • the pain is real, so people want the change
  • the work is clear and repeats every day
  • the person in charge is willing to help

When the first department works well, the other departments see it with their own eyes. That does more than any meeting.

2. Keep the old system running beside the new one

Do not switch the old system off on the first day. Run both for a while.

At the mill, the old Microsoft Access database and the new system ran side by side during the change. I wrote merge scripts that could be run again and again, so records from the old system kept arriving in the new one. Nobody had to choose a single "cut-off day" and hope.

Running both has a cost, because some work is done twice for a short time. Keep that time short and give it a clear end date. It is still much cheaper than a failed launch.

3. Bring the old data before the users arrive

A new system that opens empty feels like a toy. Staff need to see their own lots, their own customers and last month's figures on the first day.

So the old data is moved first, and checked, before the first user logs in. I wrote about that work in my Access to MySQL migration story.

4. Train people on their own screens only

Do not show everyone the whole system. A person who enters printing production needs two or three screens, not forty-five.

What works:

  • train each person at their own desk or machine, on their own work
  • give each user only the screens they need, so the menu is short
  • use the names and numbers staff already know
  • stay close for the first few days, because that is when the real questions come

Short menus are also safer. User roles and an audit trail mean a new user cannot damage another department's data while they are learning.

5. Compare the numbers every day

While both systems run, compare them. Take one figure that matters, such as today's production or the stock of one lot, and check it in the old system and the new one.

If the two match for a number of days, people start to trust the new system. If they do not match, you have found a problem while it is still small. Either way you win.

6. Fix small problems fast

In the first weeks, staff will find things nobody thought of: a field in the wrong order, a missing column in a report, a button that is too small on a tablet.

Each one is small. Together they decide whether people like the system. A fix that arrives the next day tells staff that their feedback matters. A fix that takes a month tells them to stop reporting.

7. Then switch the old system off

This step is easy to forget. If the old system stays open "just in case", some people will keep using it, and you will have two sets of numbers forever.

When a department has run on the new system and the numbers match, make the old one read-only for that department. People can still look at history. They cannot enter new data there.

What the owner must do

The developer cannot do this part.

  1. Say clearly that the new system is the official one. If a report is not from the system, do not accept it.
  2. Name one person in each department who answers questions and collects problems.
  3. Read the system's reports yourself. When staff see the owner using the numbers, they enter them carefully.
  4. Be patient for the first month. Work is a little slower while people learn. After that it is faster than before.

A simple order to follow

  1. Move and check the old data
  2. Go live in one department, with the old system still running
  3. Compare numbers daily and fix problems fast
  4. Make the old system read-only for that department
  5. Repeat for the next department

It is slower than one big switch. It is also the way that still works three months later.
